# Browser Extension Mail Cleaner — v1 Design

## Context

`yahooMailCleaner` (a separate, already-shipped project) is a personal
Python CLI that classifies and bulk-cleans a mailbox over IMAP, using a
default-deny domain-trust model: a message is only treated as
legitimate if its sender's domain is in an explicit trusted set (a
user-maintained allowlist, a hardcoded list of ~150 major brand
domains, or any `.gov` domain). Everything else is flagged by default.
That architecture was validated against two real inboxes (a Yahoo
account with a ~50,000-message backlog, cleaned down to ~2,000, and a
Gmail account) over the course of building it.

This project ports that same idea into a distributable product: a
Chrome extension that runs entirely on the end user's own machine,
using their own Gmail login, rather than a script the user runs
locally against their own IMAP credentials. The CLI is not being
replaced — it continues to exist as its own project, for its own
purpose (personal, credential-based, provider-agnostic cleanup). This
is a new product built on the same classification idea, targeting
distribution to other people.

The motivating reason for a browser extension specifically, over a
hosted multi-tenant service: it never requires holding another
person's credentials. The extension runs inside the user's own
authenticated browser, using Google's OAuth consent flow — the user
grants access from their own Google account, and can revoke it from
there at any time. This avoids the trust problem that sank Unroll.me
(caught in 2017 reselling the mailbox access it centrally held) and
avoids ever needing a server that stores anyone's credentials.

## Functional Requirements

- **FR1** — The extension authenticates via Google OAuth
  (`chrome.identity.getAuthToken`), scoped to `gmail.readonly`,
  `gmail.modify`, and `gmail.send`. No IMAP, no app passwords, no
  credentials of any kind stored by the extension.
- **FR2** — On a scan (triggered from the popup), the background
  service worker fetches message headers only (via the Gmail API's
  `users.messages.get` with `format=metadata` and an explicit
  `metadataHeaders` list: `From`, `Subject`, `List-Unsubscribe`,
  `List-Unsubscribe-Post`, `Authentication-Results`) for every message
  in the inbox — mirroring the CLI's `BODY.PEEK[HEADER]` IMAP fetch,
  never full message bodies.
- **FR3** — Each message is classified using the same default-deny
  logic as the CLI: not flagged only if its domain is in the trusted
  set (user's allowlist ∪ `KNOWN_BRAND_DOMAINS` ∪ `.gov`); otherwise
  flagged, with the same diagnostic nets (auth failure, suspicious
  local-part, padding evasion, list-unsubscribe-present, suspicious
  TLD) used only to produce a more specific reason label, never to
  change the flagged/not-flagged outcome.
- **FR4** — Classification logic (`classify.js`, `headers.js`, ported
  from the CLI's `classify.py`/`headers.py`) is pure — no browser API
  calls, no network access — so it is unit-testable the same way the
  Python version is.
- **FR5** — The trusted-domain set is the union of `KNOWN_BRAND_DOMAINS`
  (a hardcoded JS port of the CLI's list) and a user-specific allowlist
  stored in `chrome.storage.sync`, which replaces `allowlist.txt`.
  Suffix-aware matching (e.g. `alerts.chase.com` matches an allowlisted
  `chase.com`) is preserved from the CLI's `is_verified_domain` logic.
- **FR6** — Scan results are aggregated by domain (mirroring the CLI's
  `aggregate_by_domain`) and cached in `chrome.storage.local`.
- **FR7** — The popup displays a digest: the count of flagged messages,
  the number of distinct flagged senders, and an estimated storage
  size reclaimable, with one primary action ("Clean my inbox").
- **FR8** — "Clean my inbox" opens a full-tab review page listing every
  flagged domain (count, reason, a sample sender), each with a
  checkbox (checked by default) and a per-domain "Trust this sender"
  action. Nothing is acted on until the user confirms from this page —
  the same scan-then-review-then-execute separation as the CLI's NFR1.
- **FR9** — "Trust this sender" immediately adds that domain to the
  `chrome.storage.sync` allowlist and removes it from the current
  review list — no separate save step.
- **FR10** — Confirming the review page triggers, for every still-checked
  message: an unsubscribe attempt (HTTP one-click POST per RFC 8058 if
  `List-Unsubscribe-Post` is present, else a plain GET; for a
  `mailto:`-only `List-Unsubscribe`, sending via the Gmail API's
  `users.messages.send` instead of raw SMTP, since a browser cannot
  open an SMTP connection), followed by moving the message to Gmail's
  Trash via the Gmail API (add the `TRASH` label, remove `INBOX`) —
  never a permanent delete.
- **FR11** — A failed unsubscribe attempt never blocks the
  corresponding trash action, matching the CLI's actioner design.

## Non-Functional Requirements

- **NFR1 (No credential custody)** — The extension never stores, sees,
  or transmits the user's Google password. All access is through
  OAuth tokens Google issues and the user can revoke independently at
  any time from their own Google Account settings.
- **NFR2 (No server dependency for core functionality)** — Scanning,
  classifying, reviewing, and executing all happen client-side, in the
  user's own browser, calling the Gmail API directly. No backend is
  required to ship or run v1.
- **NFR3 (Reversibility)** — "Delete" always means moving to Gmail's
  Trash (which Gmail auto-purges after 30 days on its own), never an
  immediate permanent delete.
- **NFR4 (Testability)** — Classification and header-parsing logic is
  pure and unit-tested with Node's built-in `node:test` runner — no
  new test-framework dependency, matching the CLI project's existing
  minimalism. Gmail-API-calling code is exercised manually against a
  real account (loaded unpacked, Developer Mode), the same "network
  code isn't unit tested" precedent as the CLI's `imap_client.py`.
- **NFR5 (OAuth scope, v1)** — The Google Cloud OAuth consent screen
  stays in **Testing** publishing status (up to 100 explicitly listed
  test users), avoiding Google's public-app verification review for
  v1. Moving to Production/public distribution is a deliberate later
  decision, not required to build or personally use v1.
- **NFR6 (Gmail-only)** — v1 targets Gmail exclusively. Yahoo Mail has
  no equivalent public, extension-friendly API, so it is out of scope
  for this project (the existing CLI remains the way to clean a Yahoo
  inbox).

## System Design

### Architecture

A Manifest V3 Chrome extension, three components, no server:

```
┌─────────────────────────────────────────────────────────┐
│ Background service worker (background.js)                │
│  - OAuth token handling (chrome.identity)                 │
│  - Gmail API calls (list/get headers, trash, send)        │
│  - classify.js / headers.js (pure, ported from the CLI)   │
│  - Reads/writes chrome.storage.local (scan cache)          │
│  - Reads/writes chrome.storage.sync (allowlist)            │
└─────────────────────────────────────────────────────────┘
         ▲                                   ▲
         │ chrome.runtime.sendMessage        │
┌────────┴────────┐                 ┌────────┴─────────┐
│ Popup (popup.html)│                 │ Review tab        │
│  - Digest card UI  │                 │ (review.html)     │
│  - Triggers a scan │                 │  - Per-domain list │
│  - Opens review tab│                 │  - Confirm/Trust   │
└────────────────────┘                 └────────────────────┘
```

No content scripts are needed — the background worker talks to the
Gmail API directly over `fetch()`, it does not need to be injected
into `mail.google.com` at all.

### Components

- **`manifest.json`** — declares `"identity"` and `"storage"`
  permissions, the OAuth2 client ID + scopes, the background service
  worker, popup, and icon.
- **`background.js`** — orchestrates everything: requests a token
  (`getAuthToken({interactive: false})` first for a silent refresh,
  falling back to `interactive: true` only when that fails), fetches
  headers, classifies, aggregates, caches, and executes confirmed
  actions.
- **`classify.js` / `headers.js`** — direct ports of the CLI's pure
  classification and header-parsing functions. No behavior changes;
  only the input shape differs (Gmail API's `payload.headers` array
  instead of a raw IMAP header block), handled by a small adapter
  function that extracts the same fields the CLI's `headers.py` does.
- **`popup.html` / `popup.js`** — reads the cached digest from
  `chrome.storage.local`, renders the count-led card (junk count large,
  storage-reclaimable badge underneath — the design validated in the
  visual mockup session), and a "Clean my inbox" button that opens
  `review.html` in a new tab.
- **`review.html` / `review.js`** — reads the cached per-domain
  aggregation, renders the checklist with "Trust this sender" per row,
  and on confirm sends a message to `background.js` to execute.

### Data flow

```
User clicks toolbar icon
        │
        ▼
Popup requests cached digest (chrome.storage.local)
   │ (or "Scan now" if none cached / stale)
   ▼
Background worker: getAuthToken → Gmail API list+get(headers)
        │
        ▼
headers.js adapter → classify.js (same default-deny logic)
        │
        ▼
Aggregate by domain → chrome.storage.local (scan cache)
        │
        ▼
Popup digest updates ──▶ "Clean my inbox" ──▶ review.html
                                                    │
                                    user reviews, unchecks/trusts
                                                    │
                                                 Confirm
                                                    │
                                                    ▼
                              Background worker: per confirmed message —
                              unsubscribe (HTTP or Gmail API send) → Trash
                                                    │
                                                    ▼
                                  "Trust this sender" writes → chrome.storage.sync
```

### Error handling

- Token acquisition failure (revoked/expired, silent refresh fails):
  prompt the user via the popup to re-authenticate (interactive OAuth),
  matching the CLI's fail-safe-not-fail-silent posture.
- Gmail API rate-limit responses (429 / quota errors): retry with
  exponential backoff, same spirit as the CLI's IMAP retry logic —
  never crash the whole scan over one throttled request.
- A failed unsubscribe attempt is recorded but never blocks that
  message's move to Trash (FR11) — identical to the CLI's actioner
  design.
- Any single message's classification or fetch failure is isolated
  and logged, not allowed to abort the whole scan.

### Testing strategy

- `classify.js` / `headers.js`: full unit test coverage via `node:test`
  — port the CLI's existing test cases directly (same inputs, same
  expected outcomes), since the logic itself isn't changing.
- Everything touching `chrome.*` APIs or the Gmail API is exercised
  manually against a real Gmail test account, loaded unpacked in
  Developer Mode — no live-network code in the automated suite, same
  as the CLI project.

## Out of scope for v1 (deferred, not rejected)

- **LLM-assisted allowlist auto-triage** (the Groq/RDAP pipeline from
  the CLI) — needs a decision on the API-key-exposure problem
  (bring-your-own-key vs. a small proxy backend) that doesn't block
  shipping a working v1 without it. The review page's "Trust this
  sender" action is v1's only allowlist-growth mechanism.
- **Scheduled/background scanning** (`chrome.alarms`) — v1 is
  click-to-scan only. Automatic daily scans are a clean, independent
  follow-up once the manual flow is proven.
- **Yahoo Mail support** — no accessible public API for a third-party
  extension; out of scope for this project entirely (NFR6).
- **Chrome Web Store publication / public OAuth verification** — v1
  targets personal use and up to 100 invited test users via OAuth
  Testing mode (NFR5). Going public is a distinct, later decision.
- **Outlook/Microsoft 365 support** — verified feasible (Microsoft
  Graph has a real REST API for mail, works for personal Outlook.com
  accounts too, standard OAuth delegated permissions, no commercial-
  approval gate). Architecturally identical work to the Gmail
  integration, so it's a real v2 provider, not a new pattern. Not
  Yahoo — Yahoo's proprietary Mail API is gone; what remains is
  OAuth2-as-IMAP-login gated behind a Commercial Access Agreement, and
  IMAP can't be spoken directly from extension JS regardless, so it
  would require a server-side proxy — which breaks NFR2 (no server
  dependency) rather than just adding work. Yahoo stays on the
  existing CLI, not this project.
- **Date-range and Gmail-category (Social/Promotions/Updates/Forums)
  filtering, combined with domain-trust classification** — the
  validated fast-follow after v1 ships. Gmail's own search can already
  filter by date, and Gmail already computes category labels
  (`CATEGORY_SOCIAL`, `CATEGORY_PROMOTIONS`, etc., readable per message
  via the Gmail API) — neither of those alone is new. What's missing
  from Gmail natively is combining them with the trust classifier:
  e.g. "everything in Promotions, older than 2 years, from a domain
  never verified as trusted" as one guided bulk action. This adds two
  new filter dimensions to the existing review-page data model (date
  range on `internalDate`, category via existing Gmail labelIds) — no
  new classification concept, just additional facets alongside the
  existing flagged/domain data already being fetched and displayed.

## Verification

1. `node --test` on `classify.js`/`headers.js` — all ported test cases
   pass, including the real-data-derived cases from the CLI (padding
   evasion, suspicious local-part, `.gov` trust, suffix-aware allowlist
   matching).
2. Load the extension unpacked in Chrome (Developer Mode) against a
   real Gmail test account with the OAuth consent screen in Testing
   mode; confirm the OAuth prompt appears, a token is issued, and a
   scan completes without needing the app to be verified.
3. Confirm the popup digest matches a manual count from the review
   page's per-domain list.
4. Confirm "Trust this sender" removes that domain from the review
   list immediately and persists in `chrome.storage.sync` (verify by
   reloading the extension and re-scanning — that domain should no
   longer appear flagged).
5. Confirm a full review → confirm cycle: unsubscribe attempts fire
   for messages with a `List-Unsubscribe` header, and all confirmed
   messages land in Gmail's Trash (not permanently deleted) — spot
   check in the real Gmail account.
6. Confirm a message from an allowlisted domain is never included in
   scan results, and a message from a domain not in the trusted set
   always is, regardless of message volume — matching the CLI's
   validated default-deny behavior.
